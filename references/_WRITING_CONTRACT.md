# 知识库写作契约（所有 `references/` 下的消费层文档都必须遵守）

> 这份文件是**内部规范**，不是给用户读的。它把"这个 skill 凭什么让人信"变成可执行的规则。
> 任何向 `decide.md` / `playbook.md` / `course_learned.md` / `course_notes.md` 写入内容的人
> （无论人还是 agent）都要先读这一份。

---

## 1. 证据分级（**每条论断都必须能归到其中一级**）

写作时用行内标记，**不允许不标**：

| 标记 | 含义 | 什么情况下能用 |
|---|---|---|
| `[官方]` | 官方明文（VASP wiki / 官方文档） | 你能给出具体的 wiki 页面名或 `references/official/` 里的文件 |
| `[算例]` | 真实输入/输出文件里的事实 | 你能给出算例路径 + 具体是哪个文件、哪一行/哪个字段 |
| `[讲义]` | 课程讲义原话 | 能给出 `L1 P28` 这类**页码引用** |
| `[答疑]` | 课程答疑原话 | 能给出 `D2-P14` 这类**段落引用** |
| `[实测]` | **本项目构建过程中真的跑出来的结果** | 你能给出"用什么命令、得到什么数" |
| `[经验]` | 有适用范围的经验判据（**不是硬规则**） | 必须同时写清"在什么条件下成立"与"反例/例外" |
| `[待核对]` | 只有单一来源，或你自己推出来的 | **默认状态**；拿不准就用它 |

### 引用格式（会被 `_audit_citations.py` 用脚本核对，写错就报红）

```
L1 P28            → references/raw/L1.txt 里的第 28 页（共 82 页）
D2-P14            → references/raw/D2.txt 里的第 14 段
references/official/pages/ISMEAR.md      → 官方层文件
things to study/day1/fe2o3/INCAR         → 真实算例文件
```

**引用必须指向真实存在的页/段。** 页号越界、段号越界都会被抓出来。
举例说明"坏写法"时，页号写成 `L1 P##` 占位形式（审计的正则只认数字，`##` 会被天然跳过）。

## 2. 三类内容**绝不混写**

| 类别 | 特征 | 怎么写 |
|---|---|---|
| **硬规则** | 官方有明文、无例外 | 写成规则 + `[官方]` + 具体页面 |
| **经验判据** | 有适用范围、有反例 | 写清"**在什么条件下成立**" + 反例 + `[经验]` |
| **待核对** | 单一来源 / 自己推的 | 显式标 `[待核对]`，**绝不包装成事实** |

> 本项目的底线：**没有溯源的结论，不许写成像事实。**

---

## 3. 决策条目必须写四件东西（缺一不可）

```
**遇到**「<可识别的处境>」→**选** <Y>
**因为**：<物理/工程上的理由>
**代价**：<这么选的代价、什么时候不该这么选>
**证据**：<标记 + 出处>
```

❌ 百科式（没用）：`ISMEAR 是展宽参数，控制部分占据……`
✅ 决策式（有用）：`遇到金属体系做几何优化 → 选 ISMEAR=1 [官方]…，因为…，代价是…`

**"因为"与"代价"都不能省。** 只说"推荐 Y"的条目，在用户遇到你没覆盖的情形时毫无帮助
—— 而用户**一定会**遇到你没覆盖的情形。

---

## 4. 症状→处方条目必须四要素齐全

1. **症状** —— 用户**能观察到**什么。最好直接给输出里的**原文片段**（可 grep）
2. **诊断** —— 为什么会这样（写**确认过的**原因，不写"可能是"）
3. **处方** —— **改哪一处、改成什么**。给具体到行的动作，不给方向
4. **判据** —— **怎么知道改对了**（可观察的指标）

> ⚠️ 最值钱的一类：**"程序不报错、但结果是错的"**。
> 这类没有任何报错提示，只在用户的算例上暴露。**专门去找它、专门去写它。**

---

## 5. 数值必须带「适用范围」

任何阈值（收敛判据、能量差、步长、截断、k 点密度、真空层厚度）都要写清三件事：

- **出处在哪**（哪个官方页面 / 哪个真实算例 / 你实测）
- **在什么体系上成立**
- **反例或例外**

**写清适用范围，比写得多更重要。**

---

## 6. "坑"要写成能复查的形式

不要写"这个参数要小心"（无法复查、无法执行）。要写成：

> **症状**（可观察）+ **原因** + **怎么避免** + **万一已经踩了怎么补救**

并尽量给**一个能自查的动作**（一条命令、一个该看的文件、一个该算的量）。

---

## 7. ⛔ 红线（违反即返工）

1. ❌ **不要把站点信息写进仓库**。禁止出现：集群地址、队列名、核数上限、账号、
   密钥、某台机器的绝对路径、`module load` 的具体模块版本。
   **要写的是方法**（"上线前先跑一个极小算例"），不是那台机器的参数。
2. ❌ **不要把 `POTCAR` 的内容放进仓库**（含片段、含 ENMAX 之外的正文）。
   可以写"某贵金属赝势的 ENMAX 约 XXX eV"这种**数字级**引用吗？—— **不可以**，
   数字也必须来自用户自己的 POTCAR 或公开的 `ZVAL`/`ENMAX` 讨论；
   写作时优先说"用 `parse_potcar_header` 读你自己的 POTCAR"。
3. ❌ **不要声称你验证过但实际没验证的事**。
4. ❌ **不要用"放宽判据"来消灭红灯**。红了先问：是判据太严，还是被检对象真的错了？
5. ❌ **不要写"某内容不存在/零命中"**，除非你给出了检索式与检索范围
   （写法见 `MAINTENANCE.md` §4.2 的教训）。

---

## 8. 冲突怎么裁（权威序）

```
references/official/（官方 wiki，含抓取日期）
        ↓ 官方没写
真实算例文件（things to study/ 下的 INCAR/OUTCAR/…）
        ↓ 算例没覆盖
讲义正文 L1–L4
        ↓
答疑稿 D1–D4
        ↓
你自己推出来的
```

**冲突要记录，不要默默选一个。** 记录格式：

```
| 位置 | A 怎么说 | B 怎么说 | 裁定 | 依据 |
```

**特别提醒**：讲义与答疑都是**二手**；`[官方]` 与 `[算例]` 优先。
但"算例里这么写"**不等于**"这么写是对的" —— 真实算例也会有笔误。
两者冲突时按上表裁定，并**把裁定理由写出来**。
